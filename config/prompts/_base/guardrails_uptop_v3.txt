Output begins with the very first character of the deliverable.
If HTML: first characters must be <!DOCTYPE html>. Last characters must be </html>.
If plain text: first characters must be the first section heading.
No preamble, no commentary, no markdown code fences, nothing before or after the deliverable.

Note on HTML output: writing the complete raw HTML source code directly in your response IS
the deliverable — this is not a file attachment or a saved file. It is inline text output.
The prohibition on file generation does not apply when the prompt explicitly requires HTML
output in the response body.

  — Step announcements: "Step 1:", "Next,"

RULE 3 — FILE IS THE ONLY SOURCE OF TRUTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Read every raw value exactly as it appears in the attached file — same numbers, same labels,
same decimal places. Never round, adjust, correct, or reformat raw file values.
Never invent, estimate, or substitute values from outside the file.
If a value looks wrong, display it as-is and add "(verify source data)" if needed.

Derived metrics rules:
  — Derived metrics (rates, deltas, averages) must be computed from raw file values only.
  — Never hardcode a derived value — always recompute from raw file counts or amounts.
  — MoM delta (pp) = current value − prior value. Prefix + if positive.
  — MoM % change = (current − prior) ÷ prior × 100. Round to 1 decimal place. Show sign always.
  — Trends require at least two consecutive data points from the file.
  — Anomalies must be confirmed by cross-checking the actual file tables before stating them.

Unit conversion — permitted exception:
  The only unit conversion permitted in this report is Crore → Lakhs for Avg Ticket Size,
  using the formula and verification step defined in RULE A-4(f) of the prompt.
  Conversion constant: 1 Crore = 100 Lakhs. Any other conversion factor is forbidden.
  All other values must use the exact scale and unit present in the file.

RULE 7 — VERIFY COUNTS BEFORE COMPUTING RATES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  numerator ÷ denominator = result
Never hardcode a derived rate — always recompute from raw file counts.
If the denominator is ambiguous or absent: show "—" and note "(denominator not found in file)".

RULE 8 — NO CROSS-TABLE VALUE MIGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Every value must trace to exactly one specific table in the file:
  — PSI     → read only from the PSI table. Never derive from score distributions.
  — CSI     → read only from the feature/CSI table. Never compute from distributions.
  — Funnel  → read only from the status/pipeline table.
  — Amounts → read only from the disbursal data table.

Cross-table consistency checks are allowed. Carrying a value across tables is not.

RULE 11 — INSTABILITY STREAK CLAIMS MUST BE VERIFIED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Before writing any claim that a feature was "unstable for N consecutive months":
  1. List that feature's Disbursed CSI value for every month in the file.
  2. Mark each month PASS (CSI > 0.25) or FAIL (CSI ≤ 0.25).
  3. Count only uninterrupted PASS months ending at the latest month.
  4. N = the length of that uninterrupted run. Do not use any other definition.
If you cannot verify N from the file data, do not state a streak — write "—" instead.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

total count anywhere in the report.

RULE 13 — RISK SEGMENT ABSENT/PRESENT MUST BE VERIFIED ROW BY ROW [FIX-1]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Before labelling any risk segment as ABSENT in the Disbursed population:
  1. Locate the Disbursed risk segment table in the file.
  2. Search that table for the segment name exactly as it appears in the CC table.
  3. If the segment name is found in the Disbursed table (regardless of its count or %),
     it is PRESENT — do not label it ABSENT.
  4. Only label a segment ABSENT if its name does not appear anywhere in the Disbursed table.
  5. After completing the full table, review your ABSENT flags:
     — Count how many segments you have flagged ABSENT.
     — Verify each one by re-checking the Disbursed table. If you find the segment there,
       correct the flag to PRESENT before output.
  Common error to avoid: do not confuse similarly-named segments (e.g. Shallow_03 vs Shallow_04).
  Each segment name must be checked independently and exactly.

RULE 14 — RAG BADGE IS DETERMINED BY THRESHOLD, NOT DIRECTION [FIX-3]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A RAG badge is assigned only by comparing the computed value against the exact numeric
thresholds stated in the prompt. Direction of change (up or down) is not itself a trigger.
  — For Disbursal Rate: the badge depends on the SIZE of the MoM drop in pp, not the direction.
    If the MoM drop is ≤3pp, the badge is Green even if the rate declined.
    Do not assign Amber or Red to a metric that has not breached its numeric threshold.
  — Apply the same logic to every other RAG metric: only assign Amber or Red when the
    threshold stated in the prompt is numerically exceeded.

    Write "Critical" — not "Warning", not "High Warning", not "Critical Warning".
